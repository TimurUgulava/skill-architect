# Шаг 4. Собрать

Создавай файлы точечно: `Write` для новых, `Edit` для правок существующих.
Перечитай файл перед изменением; полная перезапись по памяти — главный
способ незаметно потерять содержимое.

## Frontmatter

Поля, которые Claude Code понимает на сентябрь 2026
(источник: code.claude.com/docs/en/skills). Обязательных нет; без `name`
берётся имя директории, без `description` — первая строка тела.

| Поле | Зачем |
|---|---|
| `name` | Имя для `/name` и листинга; kebab-case, совпадает с директорией |
| `description` | Что делает и когда применять — по нему модель решает, брать ли скилл |
| `when_to_use` | Дополнение к description: триггерные фразы, примеры запросов; считается вместе с ним |
| `argument-hint` | Подсказка в автодополнении: `[файл] [формат]` |
| `arguments` | Именованные позиционные аргументы → `$имя` в теле |
| `disable-model-invocation` | `true` — только ручной запуск по `/name`; для опасного, дорогого, редкого |
| `user-invocable` | `false` — только модель; фоновое знание, которого нет в меню `/` |
| `allowed-tools` | Инструменты без запроса разрешения на время вызова |
| `disallowed-tools` | Инструменты, убранные из пула, пока скилл активен |
| `model`, `effort` | Переопределить модель или уровень усилия на ход |
| `context: fork` + `agent`, `background` | Запуск в изолированном субагенте; `background: false` — дождаться результата |
| `hooks` | Хуки, регистрируемые при вызове и живущие до конца сессии |
| `paths` | Glob-шаблоны файлов: автозагрузка только при работе с ними |
| `shell` | `bash` (по умолчанию) или `powershell` для `!`-команд |
| `metadata`, `license`, `compatibility` | Свои данные, лицензия, требования к среде; Claude Code их не интерпретирует |

Подстановки в теле: `$ARGUMENTS`, `$0`/`$1`, `$имя` из `arguments`,
`${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_SESSION_ID}`.
Динамический контекст: `` !`команда` `` в начале строки или блок ```` ```! ````
выполняется до того, как модель видит текст; упавшая команда отменяет весь
вызов скилла, поэтому давай только надёжные команды.

## Description

Единственная строка, которая читается в каждом ходу каждой сессии, где
скилл установлен. Три части в этом порядке: что делает → когда применять
(фразы пользователя, типы файлов, симптомы) → когда не применять.

- **Первое предложение — главное.** Листинг обрезает `description` вместе
  с `when_to_use` на 1 536 знаках; сначала ключевой сценарий.
- **Триггерные фразы — как человек реально пишет**, включая разговорные и
  неявные формулировки, где скилл не назван.
- **Исключения — реальные near-miss**: соседние скиллы проекта, смежные
  домены, похожие слова с другой задачей. «Не для написания кода» у
  скилла про PDF — бесполезное исключение.
- **Без шагов процесса.** Description с алгоритмом внутри заставляет модель
  следовать ему и не читать тело — это наблюдалось на практике, а не
  предположение.
- **Не «настойчиво».** Перетриггеривание бьёт по соседям сильнее, чем
  недотриггеривание по самому скиллу; точность важнее напора.
- **Триггер узкий и предметный.** «Когда добавляешь или меняешь миграцию»
  работает, «при любой работе с базой данных» заставляет модель хвататься за
  скилл почти всегда. Проверь себя вопросом: назови запрос из этой же
  области, при котором скилл брать не нужно. Не назвал — описание широкое.
- **Помни про соседей по установке.** Когда скиллов много, их описания
  конкурируют за место в контексте и обрезаются; из обрезка должно быть
  понятно, что скилл берёт. Перед сборкой посмотри описания соседних скиллов
  проекта и убедись, что они не пересекаются лексически с твоим.

## Тело

Тело читается один раз при вызове и остаётся в контексте до конца сессии.

- **Что делать, а не как и почему на каждом шагу.** Причина нужна у
  жёсткого правила; у обычного шага она — лишние токены.
- **Цель и границы вместо метода.** Тест контрпримера: придумай запрос, при
  котором твоё «всегда» даёт плохой результат. Нашёл за минуту — перепиши
  в цель. Не нашёл — правило законное, оставь с причиной.
- **Три зоны императива** (`design.md`, «Защитные зоны») — там форма
  «никогда без подтверждения» сохраняется; «выполняется после
  подтверждения» — более слабая инструкция.
- **Один термин на понятие.** «Образец» везде, а не образец/эталон/пример.
- **Императив.** «Извлеки», «покажи», не «ты должен извлечь».
- **Без ритуалов.** Нет «критически важно», «обрати особое внимание»,
  капса; они не усиливают, а обесценивают.
- **Маршруты к ветвям — таблицей «файл → когда открыть».**
- **Внешние действия** — отдельным блоком: что показать человеку, чего
  ждать, что делать при отказе.
- **Раздел «Готово, когда»** — обязателен. Проверяемый список из карты
  работы (`process-design.md`) плюс строка «пока это не так — доводи сам, не
  спрашивай». Без него модель приходит за одобрением на первом же варианте.
- **Раздел «Можно без вопросов»** — обязателен рядом с запретами. Короткий
  список обратимых действий внутри рабочей зоны скилла.
- **Не пиши того, что модель умеет сама.** «Прогони тесты», «проверь себя»,
  «рассуждай шаг за шагом», «будь внимателен» — она это делает и без
  напоминания, а напоминание заставляет делать лишний раз и невпопад.
- **Не требуй читать всё перед каждым шагом.** Вместо «перед любой правкой
  открой три справочника» — маршрут: что где лежит, модель откроет нужное.
- **Ничего о пользователе.** Его вкусы и факты — в памяти Claude или в
  образцах, не в теле.

## References

Одна тема на файл, имя говорит о содержимом, условие чтения стоит в
`SKILL.md`. Файл длиннее трёхсот строк получает оглавление.

У нормы один адрес — и это проверяется механически, а не намерением:
каждое число, порог, список маркеров, формулу и факт, которые ты написал
в `SKILL.md`, найди поиском по `references/`, и наоборот. Нашёл второй
раз — оставь там, где применяется, а в другом месте замени ссылкой.
Особенно коварны «краткие напоминания» в корне того, что подробно
расписано в ветви: через месяц правки доедут только до одной копии.

## Scripts

Для хрупкого, точного, повторяющегося: разбор форматов, вызовы API, расчёты,
проверки. Требования: `#!/usr/bin/env python3` или `bash`; `--help` с
описанием аргументов; говорящие имена аргументов; ошибки текстом в stderr
и ненулевой код; ни одного захардкоженного пути, токена или адреса.
Ссылки на скрипт из тела — через `${CLAUDE_SKILL_DIR}/scripts/…`.

## Assets и образцы

Образцы вкуса — только утверждённые автором, с пометкой источника (дата,
где опубликовано). Шаблоны вывода — как файл, а не как текст в теле.

## Чего в скилле не должно быть

`README.md` и `CHANGELOG.md` внутри директории скилла, если она не
является репозиторием скилла; инструкции по использованию инструментов
(они живут в описании инструмента); пересказ того, что видно из файловой
системы; дубли `CLAUDE.md`.

## Чек перед выдачей

Механическое проверяет скрипт, его же стоит приложить к собранному скиллу:

```
python3 ${CLAUDE_SKILL_DIR}/scripts/check_skill.py <путь к собранному скиллу>
```

Он ловит битые маршруты, осиротевшие справочники, одну норму в двух файлах,
отсутствие разделов «готово» и «можно без вопросов», капс без причины,
личные пути и похожее на секреты. Ноль находок — не гарантия качества:
содержательная оценка идёт по `rubric.md`, а поведение проверяется прогоном
(`verification.md`).

Глазами остаётся то, чего скрипт не видит: узкое ли description (назови
соседний запрос, на который скилл брать не нужно), живые ли условия чтения,
не сочинены ли образцы вкуса.

Дальше — `verification.md`.
