# Шаг 2. Спроектировать

Выход шага — архитектура на утверждение: результат и его мера, паттерн и
степень свободы, дерево файлов с условиями чтения, схема логики, защитные
зоны, решения по frontmatter. Переделать здесь дешевле, чем после сборки.

## Три вопроса до всего остального

Запиши ответы — они пойдут в тело скилла и в рубрику проверки:

1. Что здесь считается правильным результатом?
2. Чем измеряется приближение к нему: тест, схема, сверка с источником,
   утверждение автором, рубрика?
3. Кто разрешает спор, когда модель и человек расходятся?

Нет ответа хотя бы на один — это развилка, вернись в `discovery.md`.

## Паттерн и степень свободы

Паттерн выбирай по `patterns.md`; их можно сочетать. Степень свободы —
отдельное решение, не следствие паттерна.

| Свобода | Когда | Форма |
|---|---|---|
| Низкая | Хрупко, должно быть точно, необратимо, нужна побайтная воспроизводимость | Скрипт с параметрами; модель его вызывает, не переписывает |
| Средняя | Есть предпочтительная процедура, допустимы вариации | Нумерованные шаги с целью каждого; модель выбирает способ внутри шага |
| Высокая | Несколько верных ответов, решает вкус или контекст | Цель, границы, рубрика, эталоны; никакой пошаговой инструкции |

Ошибка старых скиллов — низкая свобода по умолчанию: «атомарные
детерминированные шаги» для задач, где важен результат, а не путь. Модель
поколения Claude 5 выбирает метод сама; предписывай его только там, где
цена ошибки высока или нужна воспроизводимость.

## Дерево файлов

```
skill-name/
├── SKILL.md          маршрутизатор: назначение, подводные камни, ход работы, маршруты
├── references/       ветви: одна тема на файл, имя говорит о содержимом
├── scripts/          детерминированное и хрупкое; исполняется, не читается
├── assets/           образцы и шаблоны для вывода; не грузятся в контекст
└── evals/            контрольные задачи и триггерные запросы (см. verification.md)
```

Правила дерева:

- **Корень несёт назначение, подводные камни и маршруты, но не ветви.**
  Тело `SKILL.md` остаётся в контексте до конца сессии, каждая строка —
  повторяющаяся плата. Документация просит держать его короче 500 строк;
  хороший маршрутизатор обычно втрое короче.
- **У каждой ветви — условие чтения**, которое выводится из того, что
  видно до открытия файла: «открой при рубрике X», «открой, если в запросе
  есть URL», «открой на шаге 3». Ветвь без условия чтения — потерянная.
- **Глубина — две ступени.** На третьей условие чтения уже не выводится.
- **Короткий блок, нужный почти всегда, остаётся в корне.** Выносить ради
  выноса — потеря, а не экономия.
- **Уникальная процедура, нужная в нескольких скиллах, — отдельный скилл**,
  а не общий референс, который каждый правит под себя.

## Интерфейс вместо примеров

Примеры вызова инструментов и «вот так надо» зажимают модель в показанное
пространство. Механику несёт структура:

- скрипт с говорящими аргументами и `--help`, а не три примера его вызова;
- перечисление допустимых статусов вместо описания, какие бывают;
- схема входа и выхода (JSON, frontmatter, таблица) вместо словесного
  описания полей;
- поведенческое ограничение как часть интерфейса: «только один пункт в
  статусе in_progress» задаёт поведение без инструкции.

Пример остаётся там, где он носитель вкуса: как звучит текст автора, как
выглядит утверждённый макет. Это референс, а не костыль, и он идёт в
`assets/` или `references/` с маршрутом, а не в тело.

## Богатые референсы

| Вместо описания словами | Дай |
|---|---|
| «Пиши живо», «тон дружелюбный», «структура логичная» | Маршрут к реальному образцу автора; несколько, если жанров несколько, и правило, какой когда брать |
| Длинный текст «как выглядит хорошо» | Рубрику: список проверяемых критериев, по которой можно запустить судью в чистом контексте |
| Описание формата на несколько экранов | Один готовый образец плюс две строки, чем он хорош |
| Описание структуры данных или контракта | Саму структуру: схему, тип, пример файла |
| Пара «черновик → принятая версия» без дела | Эталон: расхождение между версиями и есть требование |

Образцы вкуса не сочиняй. Где правильность решает вкус, образец — только
тот, что автор утвердил или опубликовал; нет образцов — попроси или
сделай первый результат и попроси утвердить, а до тех пор скилл честно
работает без эталона и говорит об этом. Где правильность объективна,
образцом служит тест, схема, эталонный вывод.

Один образец якорит: все результаты станут его вариациями. Два-три разных
плюс правило выбора — лучше одного идеального.

## Защитные зоны

Единственные места, где жёсткость обязательна, и там она остаётся
императивом с причиной:

- **Внешние необратимые действия** — отправка, публикация, платёж,
  удаление, вызов стороннего сервиса с побочным эффектом. Скилл показывает,
  что и куда уйдёт, и ждёт подтверждения человека. Для таких скиллов
  рассмотри `disable-model-invocation: true`: запускаться только по `/имя`
  руками, не по догадке модели.
- **Секреты и личные пути** — не в скилле. Ключи через окружение или
  Keychain, пути через `${CLAUDE_SKILL_DIR}` и `${CLAUDE_PROJECT_DIR}`.
- **Закон, приватность, фактчек** — утверждённые формулировки дословно;
  суждением модели не заменяются.
- **Известная боль проекта** — правило, заведённое после конкретной
  ошибки, остаётся с датой и причиной.

Всё остальное — цель и границы.

## Механика frontmatter как архитектурные решения

Часть поведения задаётся полями, а не текстом (полный список полей —
в `writing.md`):

| Решение | Поле |
|---|---|
| Запуск только руками, без автовызова (опасное, дорогое, редкое) | `disable-model-invocation: true` |
| Фоновое знание, которое пользователь не вызывает сам | `user-invocable: false` |
| Изолированный контекст — длинный или шумный процесс | `context: fork` + `agent`, при необходимости `background: false` |
| Разрешить инструменты без вопросов на время вызова | `allowed-tools` |
| Убрать инструмент из пула (например, вопросы в фоновом цикле) | `disallowed-tools` |
| Включаться только при работе с файлами определённого вида | `paths` |
| Именованные аргументы `/skill foo bar` | `arguments`, `argument-hint` |
| Живые данные в момент запуска (ветка, статус, дата) | `` !`команда` `` в теле |

## Схема и утверждение

Нарисуй Mermaid-схему логики *будущего скилла* — от триггера через
развилки к результату — и покажи дерево файлов с условием чтения у каждой
ветви. Спроси одно: «Архитектура верна, собираю?» Дальше — `writing.md`.
